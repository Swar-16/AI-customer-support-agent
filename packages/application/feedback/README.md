# Feedback Application Layer

## Overview

The `packages/application/feedback/` package implements the application-layer workflow for collecting, reviewing, and querying customer feedback about AI-generated support responses.

It provides three complementary operations:

```text
Customer
   │
   │ Submit feedback
   ▼
submit_feedback.py
   │
   ▼
Feedback
status = pending
   │
   │ Staff review
   ▼
review_feedback.py
   │
   ├── reviewed
   ├── actioned
   └── dismissed

Query / History / Review Queue
   │
   ▼
query_feedback.py
```

The package is responsible for:

* accepting authenticated customer feedback;
* validating that feedback refers to a legitimate AI-generated response;
* enforcing customer ownership of conversations;
* preventing duplicate or conflicting submissions;
* maintaining feedback lifecycle state;
* allowing authorized support staff to review feedback;
* enforcing optimistic concurrency using `row_version`;
* recording feedback submission/review audit events;
* exposing customer-safe or staff-inclusive feedback views depending on the requester;
* providing filtered and paginated feedback queries.

The three files form a complete application-layer feedback workflow rather than independent utilities.

# Feedback Lifecycle

Feedback begins in the `pending` state.

The supported lifecycle is:

```text
                 ┌──────────────┐
                 │   pending    │
                 └──────┬───────┘
                        │
              ┌─────────┼──────────┐
              │         │          │
              ▼         ▼          ▼
          reviewed   actioned   dismissed
              │
              ├───────────────┐
              ▼               ▼
          actioned        dismissed
```

The transition graph defined by `review_feedback.py` is:

```text
pending
 ├──> reviewed
 ├──> actioned
 └──> dismissed

reviewed
 ├──> actioned
 └──> dismissed

actioned
 └──> terminal

dismissed
 └──> terminal
```

No transitions are allowed out of `actioned` or `dismissed`.

The supported feedback statuses used by querying are:

```text
pending
reviewed
actioned
dismissed
```

```text
AuthenticatedPrincipal

```

# Core Domain Relationship

Feedback is explicitly associated with an AI response.

A submission contains:

```text
conversation_id
response_message_id
ai_run_id
```

These relationships are verified before feedback is accepted.

The intended relationship is:

```text
Conversation
     │
     ├── Assistant Response Message
     │          │
     │          └── AI Run
     │
     └── Feedback
```

The application therefore does not treat feedback as an arbitrary standalone rating.

It verifies that the selected response actually belongs to the supplied conversation and was generated by the supplied AI run.

# 1. Submitting Feedback

## `submit_feedback.py`

`SubmitFeedback` handles customer submission of feedback against an AI response.

The command is:

```python
SubmitFeedbackCommand
```

It contains:

```text
conversation_id
response_message_id
ai_run_id
rating
principal
trace_id
helpful
comment
reason_codes
metadata
```

Customer identity is derived from the authenticated principal rather than supplied independently.

---

# Customer-Only Submission

Only authenticated customers may submit feedback.

The command rejects:

```text
SUPPORT_AGENT
ADMIN
```

and other roles.

The requirement is explicit:

```text
principal.role == CUSTOMER
```

Otherwise:

```text
FeedbackSubmissionAccessDeniedError
```

is raised.

This prevents a caller from impersonating a customer through an arbitrary `customer_id`.

---

# Customer Identity

The customer ID is derived from:

```python
command.principal.user_id
```

through:

```python
SubmitFeedbackCommand.customer_id
```

This provides a trusted identity boundary between authentication and feedback persistence.

---

# Rating Validation

Ratings must be integers from:

```text
1 → 5
```

Boolean values are explicitly rejected even though Python's `bool` is a subclass of `int`.

```text
Valid:
1
2
3
4
5

Invalid:
0
6
True
False
1.5
```

---

# Helpful Flag

`helpful` is optional:

```text
bool | None
```

If supplied, it must actually be a boolean.

This permits feedback such as:

```text
rating  = 2
helpful  = false
```

or:

```text
rating  = 5
helpful  = true
```

---

# Comment

Comments are optional.

They are:

* stripped of surrounding whitespace;
* converted to `None` when empty;
* limited to 5,000 characters.

The maximum is defined as:

```text
MAX_COMMENT_LENGTH = 5_000
```

---

# Feedback Reason Codes

The submission layer defines an allowlist of reason codes:

```text
INCORRECT_ANSWER
INCOMPLETE_ANSWER
IRRELEVANT_ANSWER
OUTDATED_INFORMATION
UNCLEAR_ANSWER
MISSING_CITATION
UNSAFE_RESPONSE
SLOW_RESPONSE
OTHER
```

Reason codes are:

* normalized to uppercase;
* stripped;
* required to be non-empty;
* deduplicated;
* restricted to a maximum of 10 values.

For example:

```text
"incorrect_answer"
" INCORRECT_ANSWER "
```

normalize to:

```text
INCORRECT_ANSWER
```

---

# Metadata

Submission metadata is accepted as a mapping but is deliberately bounded.

Constraints include:

```text
maximum keys       = 100
maximum serialized = 20,000 characters
```

Metadata keys must:

* be strings;
* not be blank;
* remain unique after normalization.

Values must be JSON serializable.

---

# Conversation Ownership

Before feedback is accepted, the application verifies:

1. the customer exists;
2. the customer is active;
3. the user has the `customer` role;
4. the conversation exists;
5. the conversation belongs to that customer.

If the conversation belongs to another customer:

```text
FeedbackConversationOwnershipError
```

is raised.

This prevents a customer from submitting feedback against another customer's conversation.

---

# Response Message Validation

The selected response message must:

* exist;
* belong to the supplied conversation;
* be assistant-authored;
* be eligible for feedback.

The application also checks message metadata.

Messages identified as:

```text
escalation_notice
lifecycle_notice
```

cannot receive AI-response feedback.

An explicit:

```text
feedback_eligible = false
```

also makes the message ineligible.

---

# AI Run Validation

The supplied AI run must:

1. exist;
2. belong to the supplied conversation;
3. have generated the supplied response message;
4. have status `completed`.

Therefore the application validates the complete provenance chain:

```text
Customer
   │
   ▼
Conversation
   │
   ▼
Assistant Response
   │
   ▼
Completed AI Run
   │
   ▼
Feedback
```

---

# Initial Feedback State

New feedback is persisted with:

```text
status = pending
```

and:

```text
reviewed_by_user_id = None
review_notes        = None
reviewed_at         = None
```

This establishes a clear separation between:

```text
customer submission
```

and:

```text
staff review
```

---

# Submission Idempotency

Feedback submissions are idempotent for a given response message.

A unique response constraint is defined:

```text
uq_feedback_response_message
```

If feedback already exists for the response, the application compares the existing values against the incoming submission.

If they are identical:

```text
created = false
```

and the existing feedback is returned.

If they differ:

```text
FeedbackSubmissionConflictError
```

is raised.

This prevents a repeated request from silently overwriting an existing customer rating.

---

# Concurrent Submission Race

The application also handles a race where two submissions arrive concurrently.

The flow is:

```text
Request A ─────┐
               ├── INSERT
Request B ─────┘
```

The database uniqueness constraint ensures only one row wins.

If the losing request receives an `IntegrityError`, the application:

1. verifies that the error corresponds to the expected unique constraint;
2. opens a fresh Unit of Work;
3. retrieves the winning feedback;
4. checks whether the winning values match;
5. returns it idempotently if identical;
6. raises a conflict if different.

A fresh transaction is required because the transaction that received the integrity error is no longer safe for normal queries.

---

# Submission Audit

A newly created feedback record generates:

```text
event_type = feedback.submitted
entity_type = feedback
action = submitted
```

The audit actor is:

```text
AuditActorType.CUSTOMER
```

and uses the authenticated customer's ID.

The recorded state includes:

```text
rating
helpful
reason_codes
status
has_comment
```

while metadata contains bounded information such as:

```text
response_message_id
comment_length
```

---

# Submission Result

Successful submission returns a detached:

```text
SubmitFeedbackResult
```

containing:

```text
feedback_id
conversation_id
customer_id
response_message_id
ai_run_id
rating
helpful
comment
reason_codes
status
row_version
created
```

The `created` field distinguishes:

```text
new submission
```

from:

```text
idempotent replay
```

# 2. Reviewing Feedback

## `review_feedback.py`

`ReviewFeedback` manages the staff-side feedback review lifecycle.

Only:

```text
SUPPORT_AGENT
ADMIN
```

may review feedback.

The command is:

```text
ReviewFeedbackCommand
```

and contains:

```text
feedback_id
expected_row_version
target_status
principal
trace_id
review_notes
```

---

# Review Authorization

The reviewer identity is derived from:

```text
principal.user_id
```

rather than a caller-supplied reviewer ID.

The application additionally verifies:

* reviewer exists;
* reviewer is active;
* persisted role matches the authenticated role;
* role is `SUPPORT_AGENT` or `ADMIN`.

---

# Review Notes

Review notes are optional for:

```text
reviewed
```

but required for:

```text
actioned
dismissed
```

The maximum review-note length is:

```text
5,000 characters
```

Whitespace is stripped, and blank strings become `None`.

---

# Review Transition Rules

The application validates every requested transition.

```text
pending
 ├── reviewed
 ├── actioned
 └── dismissed

reviewed
 ├── actioned
 └── dismissed
```

The following are invalid:

```text
actioned → anything
dismissed → anything
reviewed → reviewed
pending → pending
```

unless the requested target status is already the current status, in which case the operation is treated as an idempotent no-op.

The transition validation is implemented through `ALLOWED_FEEDBACK_TRANSITIONS`.

---

# Row-Level Locking

Before changing feedback state, the reviewer workflow retrieves the feedback using:

```text
get_by_id_for_update()
```

This locks the row during the transaction.

Conceptually:

```text
BEGIN
  │
  ▼
Lock feedback row
  │
  ▼
Validate version
  │
  ▼
Validate transition
  │
  ▼
Update
  │
  ▼
Audit
  │
  ▼
COMMIT
```

---

# Optimistic Concurrency

In addition to row locking, review requests carry:

```text
expected_row_version
```

The current database value must match the expected version.

```text
expected = 7
actual   = 7
    │
    ▼
allowed

expected = 7
actual   = 8
    │
    ▼
conflict
```

A mismatch raises:

```text
FeedbackReviewConcurrencyError
```

This protects against a reviewer acting on stale dashboard state.

---

# Idempotent Review

If:

```text
current_status == target_status
```

the operation returns successfully with:

```text
changed = false
```

No new transition is applied.

This makes repeated requests safe.

---

# Applying a Review

For an actual transition:

```text
status = target_status
updated_at = occurred_at
```

The first review establishes:

```text
reviewed_at
reviewed_by_user_id
```

These fields are preserved once populated.

Thus:

```text
first review
    ↓
reviewed_at = timestamp
reviewed_by_user_id = reviewer
```

Later transitions do not replace the original reviewer identity.

---

# Review Audit

A successful state change creates:

```text
event_type  = feedback.reviewed
entity_type = feedback
action      = reviewed
```

The actor is mapped according to the authenticated role:

```text
SUPPORT_AGENT → AuditActorType.AGENT
ADMIN         → AuditActorType.ADMIN
```

The audit contains before/after state information and bounded metadata such as:

```text
previous_status
target_status
review_notes_length
```

---

# Review Audit State

The audit state intentionally records state rather than unrestricted review content:

```text
status
reviewed_by_user_id
reviewed_at
has_review_notes
row_version
```

The boolean:

```text
has_review_notes
```

allows audit consumers to know whether notes existed without requiring the audit record to duplicate their full contents.

---

# Review Result

`ReviewFeedbackResult` provides a detached post-operation representation:

```text
feedback_id
conversation_id
customer_id
response_message_id
ai_run_id
previous_status
current_status
reviewed_by_user_id
review_notes
reviewed_at
row_version
updated_at
changed
```

# Feedback View

`FeedbackView` is a detached representation of feedback.

It exposes:

```text
feedback_id
conversation_id
customer_id
response_message_id
ai_run_id
rating
helpful
comment
reason_codes
status
reviewed_by_user_id
review_notes
metadata
row_version
created_at
updated_at
reviewed_at
```

The view uses immutable dataclass semantics.

It also converts:

```text
reason_codes → tuple
metadata     → MappingProxyType
```

to prevent callers from mutating the returned application representation.

---

# Customer vs Staff Visibility

The query layer has an explicit information boundary.

For:

```text
CUSTOMER
```

internal review information is hidden.

For:

```text
SUPPORT_AGENT
ADMIN
```

internal review information is included.

Customer-visible feedback therefore excludes:

```text
reviewed_by_user_id
review_notes
metadata
reviewed_at
```

while staff views can include them.

---

# Get One Feedback Record

`GetFeedback`:

1. validates the query;
2. validates the Unit of Work;
3. validates the authenticated requester;
4. loads the feedback;
5. checks access;
6. builds the appropriate feedback view.

If the feedback does not exist:

```text
FeedbackDoesNotExistError
```

is raised.

---

# Access Control

Support agents and administrators can access feedback.

Customers can access only feedback where:

```text
feedback.customer_id == principal.user_id
```

If a customer requests another customer's feedback, the application intentionally raises:

```text
FeedbackDoesNotExistError
```

rather than revealing that the record exists.

This provides resource-existence concealment.

---

# Listing Feedback

`ListFeedbackQuery` supports:

```text
status
rating
helpful
reason_code
customer_id
conversation_id
created_from
created_to
limit
offset
```

The operation can therefore serve two use cases:

```text
Customer
  └── own feedback history

Support/Admin
  └── review queue / dashboard filtering
```

---

# Customer Query Restrictions

Customers cannot use internal review filters.

The application rejects customer attempts to filter by:

```text
status
rating
helpful
reason_code
```

Customers also cannot query another `customer_id` and cannot use dashboard time-range filters.

For customers, the repository query is automatically scoped to:

```text
customer_id = principal.user_id
```

---

# Staff Query Filters

Staff users can use the full filter set:

```text
status
rating
helpful
reason_code
customer_id
conversation_id
created_from
created_to
```

This makes `ListFeedback` suitable for an internal review queue.

---

# Status Normalization

Feedback status filters are:

1. stripped;
2. lowercased;
3. validated against the known statuses.

Valid values are:

```text
pending
reviewed
actioned
dismissed
```

---

# Reason-Code Normalization

Reason codes are:

```text
strip()
upper()
```

normalized.

For example:

```text
" incorrect_answer "
```

becomes:

```text
INCORRECT_ANSWER
```

---

# Query Pagination

The default page size is:

```text
50
```

The maximum is:

```text
200
```

Offset must be non-negative.

The implementation fetches:

```text
limit + 1
```

records to determine whether another page exists.

```text
requested limit = 50

database fetch = 51

returned = first 50
has_more = true if record 51 exists
```

---

# Feedback Page

The result is:

```text
FeedbackPage
```

with:

```text
items
limit
offset
has_more
```

and a convenience property:

```text
count
```

which returns:

```text
len(items)
```

---

# Date Filtering

The query layer accepts:

```text
created_from
created_to
```

as timezone-aware datetimes.

Naive datetimes are rejected.

The range must also satisfy:

```text
created_from <= created_to
```

# Transaction Boundaries

## Submission

The submission workflow performs:

```text
BEGIN
  │
  ├── validate customer
  ├── validate conversation
  ├── validate response
  ├── validate AI run
  ├── check duplicate
  ├── insert feedback
  ├── record audit
  └── COMMIT
```

If the unique constraint races, a new recovery Unit of Work is opened.

---

## Review

The review workflow performs:

```text
BEGIN
  │
  ├── validate reviewer
  ├── lock feedback
  ├── validate row version
  ├── validate transition
  ├── update feedback
  ├── flush
  ├── record audit
  └── COMMIT
```

---

## Query

Queries use a Unit of Work for repository access but do not modify feedback state.

---

# Time Handling

Review operations use an injectable clock:

```python
Clock = Callable[[], datetime]
```

The default clock returns:

```text
datetime.now(timezone.utc)
```

The clock result must be timezone-aware.

This makes review behavior deterministic in tests while preserving timezone-aware timestamps in production.

# Design Invariants

The package maintains several important invariants.

### Feedback must belong to a real conversation

```text
conversation exists
```

### Customer must own the conversation

```text
conversation.user_id == customer_id
```

### Feedback must target an eligible assistant response

```text
response.conversation_id == conversation_id
response.role == assistant
```

### AI provenance must match

```text
ai_run.conversation_id == conversation_id
ai_run.response_message_id == response_message_id
ai_run.status == completed
```

### One feedback record per response

```text
response_message_id → unique feedback
```

### Review requires authorized staff

```text
SUPPORT_AGENT | ADMIN
```

### Review requires a valid lifecycle transition

```text
pending → reviewed/actioned/dismissed
reviewed → actioned/dismissed
```

### Stale review state is rejected

```text
expected_row_version != actual_row_version
        ↓
concurrency error
```

# Summary

The `packages/application/feedback/` package provides the complete application workflow for **customer feedback on AI-generated responses**.

Its responsibilities can be summarized as:

```text
                 FEEDBACK APPLICATION
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
       SUBMIT          REVIEW          QUERY
          │              │              │
          │              │              │
      Customer       Staff/Admin     Customer/Staff
          │              │              │
          ▼              ▼              ▼
       Validate       Authorize       Authorize
       Provenance     Row lock        Scope
       Ownership      Version         Filters
       Payload        Transition      Pagination
          │              │              │
          ▼              ▼              ▼
       pending       reviewed/       FeedbackView
                     actioned/
                     dismissed
          │              │
          └──────┬───────┘
                 ▼
             Audit Events
```

The central invariants are:

```text
Customer identity comes from the authenticated principal.
Only customers may submit feedback.
Customers may only submit feedback for their own conversations.
Feedback must reference a valid assistant response.
The response must be associated with the supplied completed AI run.
One feedback record exists per response.
Identical repeated submissions are idempotent.
Conflicting repeated submissions are rejected.
Only support agents and administrators may review feedback.
Review transitions follow an explicit state machine.
Actioned/dismissed reviews require review notes.
Review operations protect against stale row versions.
Queries expose different information to customers and staff.
Feedback creation and review transitions generate audit events.
Application results are detached from persistence models.
```

Together, `submit_feedback.py`, `review_feedback.py`, and `query_feedback.py` form the application-layer boundary responsible for taking feedback from **customer submission → validated persistence → staff review → controlled lifecycle → queryable history/queue**.
