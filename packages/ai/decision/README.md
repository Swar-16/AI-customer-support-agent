# Decision Layer

## Overview

The `decision` package is the deterministic workflow-routing layer of the AI customer-support agent.

It takes a **validated semantic understanding of the customer's request**—represented by `IntentResult`—and converts it into a controlled `DecisionResult` describing what the system should do next.

The package is located at:

```text
packages/ai/decision/
```

Its three components are:

```text
decision/
├── engine.py
├── policies.py
└── schemas.py
```

The package separates three concerns:

* `schemas.py` — defines the decision vocabulary and canonical decision output.
* `policies.py` — defines declarative default routing policies for every canonical intent.
* `engine.py` — evaluates runtime conditions and converts an `IntentResult` into a final `DecisionResult`.

The engine is explicitly deterministic and is intended to operate after semantic intent classification has already taken place.

---

# Purpose

The decision layer answers:

> **Given what we know about the customer's intent and the available workflow constraints, what should the system do next?**

The possible next steps are represented by:

```text
ANSWER
RETRIEVE_INFORMATION
PERFORM_ACTION
ASK_CLARIFICATION
ESCALATE
```

These decisions are not generated by an LLM in this layer. They are produced through deterministic rules and declarative policies.

This makes the layer suitable for controlled routing, evaluation, auditing, and predictable orchestration.

---

# Package Responsibilities

The decision package is responsible for:

* enforcing minimum intent-confidence requirements;
* handling explicit human-support requests;
* handling severe unresolved customer dissatisfaction;
* handling security-sensitive intents;
* handling genuinely unknown intents;
* enforcing mandatory workflow information requirements;
* resolving the default policy for a canonical intent;
* distinguishing published knowledge retrieval from operational business-data retrieval;
* allowing safe knowledge-backed guidance when appropriate;
* handling workflows that genuinely require additional information;
* producing machine-readable decision reason codes;
* producing human-readable audit-oriented reason summaries;
* attaching non-authoritative routing metadata;
* detecting inconsistencies between the intent taxonomy and decision-policy registry.

It is **not** responsible for:

* classifying the customer's intent;
* generating the final customer-facing answer;
* authorizing sensitive business actions;
* directly accessing business records;
* performing business operations.

## In particular, the policy layer explicitly states that priority and actionable metadata do not grant authorization to perform an action.

# Architecture

The package follows a two-stage decision model:

```text
                    IntentResult
                         │
                         ▼
              ┌─────────────────────┐
              │    DecisionEngine   │
              │                     │
              │ Runtime safety      │
              │ gates + precedence  │
              └──────────┬──────────┘
                         │
                         ▼
              IntentDecisionPolicy
                         │
                         ▼
                  DecisionResult
```

More specifically:

```text
IntentResult
    │
    ├── Escalation signals?
    │       ├── Human request ───────────────► ESCALATE
    │       └── Severe dissatisfaction ──────► ESCALATE
    │
    ├── Privacy/security intent?
    │       └────────────────────────────────► ESCALATE
    │
    ├── Unknown intent?
    │       └────────────────────────────────► ASK_CLARIFICATION
    │
    ├── Low confidence?
    │       └────────────────────────────────► ASK_CLARIFICATION
    │
    ├── Mandatory information missing?
    │       └────────────────────────────────► ASK_CLARIFICATION
    │
    ├── Knowledge retrieval policy?
    │       └────────────────────────────────► RETRIEVE_INFORMATION
    │
    ├── needs_clarification?
    │       └────────────────────────────────► ASK_CLARIFICATION
    │
    └── Default intent policy ────────────────► DecisionResult
```

The ordering is deliberate and is part of the engine's safety semantics.

# `schemas.py`

## Purpose

`schemas.py` defines the canonical vocabulary and output contract of the decision layer.

It uses Python `StrEnum` types for stable machine-readable values and Pydantic for validation of the final result.

---

## `DecisionType`

`DecisionType` defines the five possible workflow decisions:

```text
answer
retrieve_information
perform_action
ask_clarification
escalate
```

The corresponding enum members are:

```python
DecisionType.ANSWER
DecisionType.RETRIEVE_INFORMATION
DecisionType.PERFORM_ACTION
DecisionType.ASK_CLARIFICATION
DecisionType.ESCALATE
```

These values describe **workflow direction**, not customer-facing wording.

---

# `DecisionReasonCode`

`DecisionReasonCode` provides stable machine-readable explanations for why a decision was selected.

The design intentionally separates these codes from natural-language explanations because dashboards, evaluation systems, and routing logic should not depend on free-form prose.

The currently defined reason codes cover:

### Direct response

```text
DIRECT_INFORMATIONAL_RESPONSE
```

### Retrieval

```text
POLICY_RETRIEVAL_REQUIRED
OPERATIONAL_LOOKUP_REQUIRED
OPERATIONAL_LOOKUP_UNAVAILABLE
```

### Clarification

```text
MISSING_REQUIRED_INFORMATION
LOW_INTENT_CONFIDENCE
UNKNOWN_INTENT
```

### Action / approval

```text
ACTION_REQUEST_DETECTED
HUMAN_APPROVAL_REQUIRED
```

### Escalation

```text
CUSTOMER_REQUESTED_HUMAN
SEVERE_CUSTOMER_DISSATISFACTION
SECURITY_SENSITIVE_REQUEST
```

### Scope / policy / availability

```text
UNSUPPORTED_REQUEST
POLICY_CONFLICT
KNOWLEDGE_UNAVAILABLE
```

Not every reason code is necessarily emitted by the current `DecisionEngine`; the schema vocabulary is broader than the branches currently exercised by `engine.py`.

---

# `DecisionResult`

`DecisionResult` is the canonical output of the deterministic decision layer.

It contains:

```python
decision: DecisionType
reason_code: DecisionReasonCode
reason_summary: str
confidence: float | None
required_information: tuple[str, ...]
metadata: dict[str, Any]
```

The model is configured with:

```python
extra="forbid"
frozen=True
str_strip_whitespace=True
```

This prevents unexpected fields, makes the result immutable, and normalizes string whitespace.

---

## `reason_summary`

The human-readable summary must contain between 1 and 500 characters.

Whitespace is normalized before the value is accepted, and an empty summary is rejected.

The summary is intended for explanation/audit purposes.

It should not become a hidden source of business authorization logic.

---

## `confidence`

`confidence` is optional and constrained to:

```text
0.0 ≤ confidence ≤ 1.0
```

For the current decision engine, the intent classifier's confidence is generally propagated into the decision result.

---

## `required_information`

This field identifies information that must be obtained before an `ASK_CLARIFICATION` workflow can proceed.

Examples include:

```text
order_id
transaction_id
customer_intent
clarification
```

The schema enforces an important invariant:

```text
ASK_CLARIFICATION
    → required_information must be non-empty
```

and conversely:

```text
Any other decision
    → required_information must be empty
```

Duplicate values are removed while preserving order.

---

## `metadata`

`metadata` contains non-authoritative routing metadata.

The schema explicitly states that sensitive business decisions must not depend on arbitrary metadata.

Current engine-generated metadata can include:

```text
intent
priority
potentially_actionable
retrieval_kind
```

and escalation metadata such as:

```text
escalation_signal
priority
```

---

# `policies.py`

## Purpose

`policies.py` contains the declarative routing policy registry.

Rather than embedding an `if/elif` branch for every intent inside `DecisionEngine`, the package stores intent-specific default routing behavior in `IntentDecisionPolicy` objects.

This means adding a new intent generally requires updating the taxonomy and policy registry rather than adding another intent-specific branch to the engine.

---

# `RetrievalKind`

`RetrievalKind` identifies the broad category of information source required when a decision involves retrieval:

```text
knowledge
operational
```

### `KNOWLEDGE`

Represents published customer-support material such as:

* policies;
* FAQs;
* procedures;
* guides;
* reference material.

### `OPERATIONAL`

Represents runtime business information such as:

* order status;
* payment state;
* subscription state;
* account information.

The enum describes the **source category**, not a concrete repository or provider.

---

# `DecisionPriority`

`DecisionPriority` provides stable workflow priority metadata:

```text
low
normal
high
urgent
```

Priority is routing metadata only. It does not itself authorize sensitive actions or bypass security/business policies.

---

# `IntentDecisionPolicy`

`IntentDecisionPolicy` is an immutable dataclass describing the default routing policy for one canonical intent.

Its fields are:

```python
intent: IntentType
default_decision: DecisionType
reason_code: DecisionReasonCode
retrieval_kind: RetrievalKind | None
potentially_actionable: bool
default_priority: DecisionPriority
```

The policy represents the answer to:

> Once an intent has been classified reliably, what is the default workflow direction?

It is a **default**, not necessarily the final runtime decision. The engine may override it based on escalation signals, confidence, missing information, or other runtime circumstances.

---

# Policy Validation

`IntentDecisionPolicy` validates its own semantic consistency.

For example:

```text
default_decision = RETRIEVE_INFORMATION
    → retrieval_kind is required
```

while:

```text
default_decision != RETRIEVE_INFORMATION
    → retrieval_kind must be None
```

This prevents impossible configurations such as:

```text
ANSWER + KNOWLEDGE
```

or:

```text
RETRIEVE_INFORMATION + no retrieval source
```

---

# Current Intent Policies

The current registry defines policies for the canonical intents.

## Knowledge-backed workflows

The following intents default to knowledge retrieval:

```text
REFUND_REQUEST
PAYMENT_ISSUE
SHIPPING_ISSUE
CANCELLATION
SUBSCRIPTION_ISSUE
ACCOUNT_ISSUE
RETURN_EXCHANGE
GENERAL_QUESTION
```

They use:

```text
default_decision = RETRIEVE_INFORMATION
retrieval_kind = KNOWLEDGE
```

## Most are marked `potentially_actionable=True`, while `GENERAL_QUESTION` is not. `ACCOUNT_ISSUE` has a default priority of `HIGH`.

## Operationally constrained order status

`ORDER_STATUS` has:

```text
default_decision = ESCALATE
reason_code = OPERATIONAL_LOOKUP_UNAVAILABLE
potentially_actionable = True
priority = NORMAL
```

## This reflects the current MVP condition that no trusted operational order-data source is configured. The engine separately requires an explicit `order_id` before the workflow can proceed.

## Security-sensitive requests

`PRIVACY_SECURITY` defaults to:

```text
ESCALATE
```

with:

```text
reason_code = SECURITY_SENSITIVE_REQUEST
priority = URGENT
potentially_actionable = False
```

## The engine evaluates this intent before ordinary confidence and clarification routing.

## Conversational requests

`CONVERSATIONAL` defaults to:

```text
ANSWER
DIRECT_INFORMATIONAL_RESPONSE
```

with no retrieval requirement and `potentially_actionable=False`.

---

## Out-of-scope requests

`OUT_OF_SCOPE` defaults to:

```text
ANSWER
UNSUPPORTED_REQUEST
```

with `potentially_actionable=False`.

---

## Unknown intent

`UNKNOWN` defaults to:

```text
ASK_CLARIFICATION
UNKNOWN_INTENT
```

Although the engine handles unknown intents explicitly before normal policy resolution.

---

# Policy Registry

The internal registry is:

```python
_INTENT_DECISION_POLICIES
```

It is exposed publicly through:

```python
INTENT_DECISION_POLICIES
```

using `MappingProxyType`, making the exported mapping read-only from consumers' perspective.

---

# Policy Lookup

The main lookup function is:

```python
get_intent_decision_policy(intent)
```

It:

1. validates that the supplied value is an `IntentType`;
2. retrieves the corresponding policy;
3. raises `KeyError` if the registry is incomplete.

---

# Policy Classification Helpers

The module also provides derived sets.

## `get_knowledge_retrieval_intents()`

Returns intents whose default workflow retrieves published knowledge.

## `get_operational_retrieval_intents()`

Returns intents whose default workflow uses operational business data.

## `get_actionable_intents()`

Returns intents marked as potentially actionable.

This is descriptive metadata only and does **not** grant authorization to execute an action.

---

# Policy Registry Validation

`validate_intent_decision_policies()` verifies that the policy registry and `IntentType` taxonomy remain synchronized.

It checks:

* missing policies;
* unexpected policies;
* invalid registry key types;
* invalid policy values;
* mismatched policy keys and `policy.intent` values.

If the taxonomy and registry drift apart, the function raises a `RuntimeError` rather than silently falling back.

The module invokes this validation at import time:

```python
validate_intent_decision_policies()
```

This makes policy/taxonomy inconsistency a fail-fast application error.

---

# `engine.py`

## Purpose

`DecisionEngine` is the runtime evaluator of the decision layer.

Its input is:

```python
IntentResult
```

and its output is:

```python
DecisionResult
```

The engine does not classify intent itself. It consumes an already validated semantic result.

---

# `DecisionEngineConfig`

The engine has one configurable safety threshold:

```python
low_confidence_threshold: float = 0.60
```

The threshold must:

```text
0.0 ≤ threshold ≤ 1.0
```

Boolean values are explicitly rejected even though Python treats `bool` as a subclass of `int`.

The documentation notes that the threshold is deliberately configurable because it should eventually be calibrated from evaluation data rather than treated as a permanent constant.

---

# Decision Evaluation Order

The order in `DecisionEngine.decide()` is one of the most important parts of the implementation.

The engine evaluates:

```text
1. Explicit human-support request
2. Severe unresolved customer dissatisfaction
3. Security-sensitive intent
4. Unknown intent
5. Insufficient classification confidence
6. Deterministically required workflow information
7. Declarative intent decision policy
8. Classifier clarification requirement
```

This prevents lower-priority routing considerations from overriding explicit escalation or safety-sensitive conditions.

---

# 1. Explicit Human Request

Escalation signals are evaluated first.

If the classifier reports:

```text
EscalationSignal.EXPLICIT_HUMAN_REQUEST
```

the engine returns:

```text
decision = ESCALATE
reason_code = CUSTOMER_REQUESTED_HUMAN
priority = normal
```

The customer's explicit request takes precedence over other escalation signals.

---

# 2. Severe Customer Dissatisfaction

If the customer has a:

```text
SEVERE_CUSTOMER_DISSATISFACTION
```

signal and no explicit human request has already triggered escalation, the engine returns:

```text
decision = ESCALATE
reason_code = SEVERE_CUSTOMER_DISSATISFACTION
priority = high
```

---

# 3. Security-Sensitive Intent

`PRIVACY_SECURITY` is escalated before confidence or missing-information checks.

This means a security-sensitive intent does not need to achieve the ordinary confidence threshold to enter the escalation path.

The associated policy specifies:

```text
decision = ESCALATE
reason = SECURITY_SENSITIVE_REQUEST
priority = URGENT
```

---

# 4. Unknown Intent

An `UNKNOWN` intent produces:

```text
decision = ASK_CLARIFICATION
reason_code = UNKNOWN_INTENT
required_information = ("customer_intent",)
```

The reason summary explains that the customer's support intent cannot be determined reliably.

---

# 5. Low Confidence

If:

```text
intent_result.confidence < low_confidence_threshold
```

the engine asks for clarification:

```text
decision = ASK_CLARIFICATION
reason_code = LOW_INTENT_CONFIDENCE
required_information = ("clarification",)
```

The default threshold is `0.60`.

This check occurs before normal intent policy routing.

---

# 6. Mandatory Workflow Information

The engine independently verifies information that a workflow **always** requires.

This is deliberately separate from the classifier's `needs_clarification` flag.

For the current MVP:

```text
ORDER_STATUS
    + no order_id
        ↓
ASK_CLARIFICATION
        ↓
required_information = ("order_id",)
```

The engine documentation explicitly states that identifiers should not be required merely because they might be useful; only universally necessary information belongs in this deterministic requirement layer.

---

# 7. Knowledge Retrieval Exception

After mandatory requirements are satisfied, the engine resolves the intent's policy.

If the policy is:

```text
default_decision = RETRIEVE_INFORMATION
retrieval_kind = KNOWLEDGE
```

the engine can proceed with knowledge retrieval even if the classifier's `needs_clarification` flag is true.

This is an important distinction.

Published support knowledge can often answer general policy, procedural, or troubleshooting questions without access to a customer's private operational record.

The engine therefore allows sufficiently confident knowledge-backed requests to continue to retrieval.

---

# Knowledge Retrieval Does Not Grant Operational Access

The helper:

```python
_can_proceed_with_knowledge_guidance()
```

only permits retrieval of verified informational guidance.

It explicitly does **not** authorize:

* access to private operational records;
* customer-specific status claims;
* business actions;
* bypassing grounding;
* bypassing response guardrails.

This distinction is central to the architecture:

```text
Published knowledge
        ≠
Customer-specific operational data
        ≠
Business action authorization
```

---

# 8. Classifier-Detected Clarification

For workflows that cannot safely proceed through knowledge retrieval, the engine respects:

```python
intent_result.needs_clarification
```

When true, `_infer_missing_information()` determines what information should be requested.

Currently:

```text
ORDER_STATUS → ("order_id",)
other workflows → ("clarification",)
```

---

# Policy Translation

Once the engine has determined that the normal intent policy can be used, `_decision_from_policy()` converts the declarative policy into a `DecisionResult`.

It creates metadata containing:

```text
intent
priority
potentially_actionable
```

and adds:

```text
retrieval_kind
```

when applicable.

The method deliberately contains no branching on individual `IntentType` values.

This is what keeps the engine generic while the policy registry remains intent-specific.

---

# Reason Summaries

`_default_policy_reason_summary()` produces stable audit-oriented explanations based on the policy's decision type.

Examples:

### Retrieve knowledge

> The request requires a response grounded in published customer-support knowledge.

### Retrieve operational data

> The request requires information from an operational business-data source.

### Answer directly

> The request can proceed to response generation without additional retrieval or business action.

### Perform action

> The request requires evaluation by the business action workflow.

### Escalate

> The request requires escalation to an appropriate human workflow.

### Clarification

> Additional customer information is required before the workflow can continue.

These summaries are explanatory only; business logic and authorization must not depend on them.

# Separation of Responsibilities

The package intentionally separates deterministic routing from classification.

```text
Intent subsystem
      │
      │ IntentResult
      ▼
Decision subsystem
      │
      │ DecisionResult
      ▼
Orchestration layer
```

The intent subsystem answers:

```text
"What does the customer appear to want?"
```

The decision subsystem answers:

```text
"What workflow should the application execute next?"
```

The decision subsystem therefore does not need to know how the intent classifier produced its result.

---

# Determinism and Safety

The engine is deterministic.

For a given:

```text
IntentResult
+
DecisionEngineConfig
+
policy registry
```

the routing behavior is deterministic.

This provides several useful properties:

* reproducible routing;
* easier evaluation;
* stable audit behavior;
* predictable escalation;
* easier testing;
* clear policy ownership.

The threshold is configurable specifically to allow future calibration from evaluation data.

---

# Authorization Boundary

The decision layer describes workflow direction but does not itself authorize sensitive operations.

For example:

```text
potentially_actionable = True
```

means that an intent may eventually lead to a business action.

It does **not** mean:

```text
"the system is authorized to perform the action."
```

The policy module explicitly documents this distinction.

Likewise, `DecisionPriority` is routing metadata rather than an authorization mechanism.

---

# Error Handling

The package uses validation to detect invalid configuration and invalid inputs early.

| Situation                                                    | Behavior                  |
| ------------------------------------------------------------ | ------------------------- |
| Invalid `DecisionEngineConfig.low_confidence_threshold` type | `TypeError`               |
| Threshold outside `[0, 1]`                                   | `ValueError`              |
| Invalid `IntentResult` passed to engine                      | `TypeError`               |
| Invalid policy object fields                                 | `TypeError`               |
| Invalid retrieval semantics                                  | `ValueError`              |
| Unknown policy lookup input type                             | `TypeError`               |
| Missing policy for canonical intent                          | `KeyError`                |
| Policy/taxonomy registry drift                               | `RuntimeError`            |
| Invalid `DecisionResult` semantics                           | Pydantic validation error |

The policy registry intentionally fails fast when it becomes inconsistent with the canonical intent taxonomy.

# Important Invariants

## Decision result invariants

```text
ASK_CLARIFICATION
    → required_information != empty
```

```text
decision != ASK_CLARIFICATION
    → required_information == empty
```

These are enforced by `DecisionResult`.

---

## Retrieval policy invariant

```text
RETRIEVE_INFORMATION
    → retrieval_kind must exist
```

```text
non-RETRIEVE_INFORMATION
    → retrieval_kind must be None
```

These are enforced by `IntentDecisionPolicy`.

---

## Registry invariant

Every canonical `IntentType` must have exactly one corresponding decision policy.

The policy's internal `intent` must also match its registry key.

---

# Extending the Decision Layer

## Adding a new intent

When a new canonical intent is introduced, the expected process is:

1. Add the intent to the canonical intent taxonomy.
2. Add an `IntentDecisionPolicy` to `_INTENT_DECISION_POLICIES`.
3. Choose the appropriate:

   * default decision;
   * reason code;
   * retrieval kind, if applicable;
   * actionability metadata;
   * priority.
4. Ensure policy semantics are valid.
5. Run the registry validation.

The engine should generally **not** require a new `if intent is ...` branch.

This is an explicit design goal of the policy architecture.

---

# Changing Confidence Thresholds

The confidence threshold is configured through:

```python
DecisionEngineConfig(
    low_confidence_threshold=0.60
)
```

The threshold should remain within:

```text
0.0 to 1.0
```

The code comments indicate that future threshold values should be calibrated against evaluation data rather than treated as permanent constants.

---

# Adding Mandatory Information Requirements

Universally mandatory workflow inputs belong in:

```text
DecisionEngine._resolve_mandatory_missing_information()
```

The distinction is important:

```text
Universally required information
    → deterministic mandatory-information rule

Potentially useful information
    → should not automatically become a mandatory requirement
```

The implementation specifically documents that identifiers should not be required merely because they might be useful.

---

# Adding Escalation Signals

Explicit escalation signals are handled in:

```text
DecisionEngine._decision_from_escalation_signals()
```

The current precedence is:

```text
EXPLICIT_HUMAN_REQUEST
        ↓
SEVERE_CUSTOMER_DISSATISFACTION
```

If both are present, the explicit human request is used as the reason because it is the clearest handoff trigger.

# Design Principles

The decision package follows several architectural principles:

### 1. Deterministic routing

The final workflow decision is produced through explicit rules and declarative policies rather than free-form model reasoning.

### 2. Policy-driven intent routing

Intent-specific defaults live in `policies.py`, not in a large conditional tree inside `engine.py`.

### 3. Safety gates precede ordinary routing

Explicit escalation and security-sensitive conditions are evaluated before confidence and normal policy routing.

### 4. Knowledge and operational data are distinct

Published support information is explicitly separated from customer-specific business records.

### 5. Classification uncertainty is not the same as workflow requirements

The classifier's `needs_clarification` flag does not replace deterministic application requirements.

### 6. Metadata is not authorization

Priority and actionability describe routing behavior; they do not authorize sensitive operations.

### 7. Fail fast on configuration drift

A mismatch between the intent taxonomy and policy registry is treated as an application error.

### 8. Machine-readable reasons

Stable reason codes are used for routing, dashboards, and evaluation instead of relying on natural-language explanations.

The imported intent types are therefore upstream dependencies of the decision layer.

---

# Summary

The `decision` package is the deterministic control point between **semantic intent understanding** and **workflow orchestration**.

Its architecture is intentionally split:

```text
schemas.py
    ↓
Defines what a decision looks like

policies.py
    ↓
Defines the default behavior for each intent

engine.py
    ↓
Applies runtime safety and workflow rules
    ↓
Produces DecisionResult
```

The most important architectural property is that **the engine does not hard-code every intent's default behavior**. Instead, it evaluates universal runtime safety and workflow conditions first, then delegates intent-specific defaults to the declarative policy registry.

This allows the decision layer to remain deterministic, auditable, extensible, and independent of the implementation details of the upstream intent classifier.
